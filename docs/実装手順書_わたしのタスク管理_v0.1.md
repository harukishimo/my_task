既存のTasks表をそのまま利用し、P列`category`（`default`／`private`）を追加する。既存行のP列が空欄でも通常カテゴリとして読み込めるようにする。タスク作成・編集画面にはカテゴリ選択を追加し、`/private`ではプライベートカテゴリだけを表示する。通常画面はカテゴリで絞り込まない。

## 1. 本書の使い方

### 1.1 目的

本書は、要件定義書と技術要件書で決定した内容を、実際に作業できる順序へ落とし込んだ実装手順である。プロジェクト作成、Google Sheets準備、実装、テスト、Vercel公開、復旧までを対象とする。

### 1.2 文書間の優先順位

| 判断対象 | 正とする文書 |
|---|---|
| アプリの目的、画面、機能、受け入れ条件 | 要件定義書 |
| アーキテクチャ、API、データ、セキュリティ | 技術要件書 |
| 作業順、コマンド、確認方法 | 本実装手順書 |

矛盾が見つかった場合は、要件定義書、技術要件書、本書の順で内容を確認し、文書を更新してから実装を続ける。

### 1.3 基本ルール

- 各フェーズの完了条件を満たしてから次へ進む。
- 秘密情報をソースコード、Git、スクリーンショット、ログへ残さない。
- PreviewとProductionで別のGoogle Sheetsを使用する。
- 最初から全画面を作らず、ドメインロジック、データ層、認証、API、画面の順で積み上げる。
- 作業中に仕様変更が発生した場合は、先に要件定義書または技術要件書を更新する。

## 5. フェーズ2：Google Sheets環境の準備

### 5.1 Google Cloudプロジェクトを作成する

1. Google Cloud Consoleで新しいプロジェクトを作成する。
2. プロジェクト名を例として`personal-task-manager`とする。
3. 「APIとサービス」からGoogle Sheets APIを有効化する。
4. Google Drive APIは、アプリからファイル作成や一覧取得を行わない限り有効化しない。

### 5.2 サービスアカウントを作成する

1. 「IAMと管理」から「サービス アカウント」を開く。
2. `personal-task-manager`等の専用サービスアカウントを作成する。
3. Google Cloudプロジェクト自体への広いIAMロールは付与しない。
4. 作成したサービスアカウントのメールアドレスを控える。
5. 「鍵」からJSON形式の新しい鍵を1つ作成し、安全な場所へ一時保存する。

ダウンロードしたJSON鍵は秘密情報である。Git管理下へ移動せず、環境変数へ値を登録した後は、作業端末上の不要なコピーを削除する。

### 5.3 2つのスプレッドシートを作成する

次の2ファイルを本人のGoogle Drive上で作成する。

| 用途 | 推奨ファイル名 | 接続元 |
|---|---|---|
| 開発・Preview | わたしのタスク管理_DEV | ローカル、テスト、Vercel Preview |
| 本番 | わたしのタスク管理_PROD | Vercel Productionのみ |

各ファイルでシート名を`Tasks`へ変更し、1行目のA列からP列へ次を入力する。

```text
id,title,due_date,is_urgent,is_important,priority,status,completed_at,is_deleted,created_at,updated_at,version,comment,plan_date,plan_order,category
```

設定する内容:

- 1行目を固定する。
- 1行目を保護し、誤編集を防ぐ。
- スプレッドシートのタイムゾーンを`(GMT+09:00) Tokyo`へ設定する。
- 一般公開および「ウェブに公開」を行わない。
- サービスアカウントのメールアドレスだけを編集者として共有する。

### 5.4 スプレッドシートIDを控える

URLが次の場合、`/d/`と`/edit`の間がスプレッドシートIDである。

```text
https://docs.google.com/spreadsheets/d/SPREADSHEET_ID/edit
```

開発用と本番用のIDを混同しないよう、パスワード管理ツール等の安全な場所へ用途を付けて保存する。

### 5.5 接続確認の方針

初回のAPI接続確認は、必ず開発用スプレッドシートに対して行う。本番用への書き込みはProduction公開直前まで行わない。

## 6. フェーズ3：環境変数と秘密情報

### 6.1 `.env.example`を作成する

値を空またはダミーにした次のファイルをGit管理する。

```dotenv
APP_PASSPHRASE_HASH=
SESSION_SECRET=
GOOGLE_SERVICE_ACCOUNT_EMAIL=
GOOGLE_PRIVATE_KEY=
GOOGLE_SHEET_ID=
GOOGLE_SHEET_TAB=Tasks
APP_TIME_ZONE=Asia/Tokyo
NEXT_PUBLIC_APP_NAME=わたしのタスク管理
```

### 6.2 `.env.local`を作成する

`.env.example`をコピーし、開発用の値だけを設定する。

- `GOOGLE_SERVICE_ACCOUNT_EMAIL`: JSON鍵の`client_email`
- `GOOGLE_PRIVATE_KEY`: JSON鍵の`private_key`
- `GOOGLE_SHEET_ID`: DEVスプレッドシートID
- `GOOGLE_SHEET_TAB`: `Tasks`
- `APP_TIME_ZONE`: `Asia/Tokyo`

秘密鍵は実際の改行を含む複数行値として保存するか、改行を`\n`へ変換した1行値として保存する。アプリ側では次のように両方を扱えるようにする。

```ts
const privateKey = process.env.GOOGLE_PRIVATE_KEY?.replace(/\\n/g, "\n");
```

### 6.3 セッション署名鍵を生成する

```bash
openssl rand -base64 32
```

出力を`SESSION_SECRET`へ設定する。値をターミナルの共有ログや文書へ貼り付けない。

### 6.4 パスフレーズハッシュ生成スクリプトを用意する

`scripts/hash-passphrase.mjs`を作り、標準入力から受け取ったパスフレーズをNode.jsの`scrypt`でソルト付きハッシュへ変換する。次を満たすこと。

- パスフレーズをコマンド引数へ書かず、シェル履歴に残さない。
- `randomBytes`で毎回異なるソルトを生成する。
- ハッシュ形式にアルゴリズム名、ソルト、ハッシュ値を含める。
- 検証側では`timingSafeEqual`を使用する。
- 平文をファイルへ保存しない。

生成したハッシュだけを`APP_PASSPHRASE_HASH`へ設定する。

### 6.5 環境変数検証を実装する

`src/lib/env.ts`でZodを使い、サーバー起動時または初回参照時に次を検証する。

- 必須値が空でない。
- `SESSION_SECRET`が十分な長さである。
- `GOOGLE_PRIVATE_KEY`に秘密鍵の開始・終了行がある。
- `APP_TIME_ZONE`が`Asia/Tokyo`である。
- サーバー専用値に`NEXT_PUBLIC_`を付けていない。

`src/lib/env.ts`には`import "server-only"`を追加し、Client Componentから読み込まれた場合にビルドを失敗させる。

### 6.6 秘密情報漏えいを確認する

```bash
git status --short
git grep -n "BEGIN PRIVATE KEY"
git grep -n "APP_PASSPHRASE_HASH="
```

秘密鍵や実値がGit管理対象から見つかった場合は、コミットする前に取り除く。すでに外部へ公開した鍵は、文字列を削除するだけでなくGoogle Cloud上で無効化し、新しい鍵へ交換する。

- [ ] `.env.example`だけがGit管理される。
- [ ] `.env.local`はDEVスプレッドシートを参照する。

export type Priority = "P1" | "P2" | "P3" | "P4";

### 7.3 優先度算出を実装する

`src/lib/tasks/priority.ts`に副作用のない関数を作る。

| 緊急 | 重要 | 結果 | 表示文言 |
|---:|---:|---|---|
| はい | はい | P1 | 今すぐやる |
| いいえ | はい | P2 | 予定する |
| はい | いいえ | P3 | 手早くやる |
| いいえ | いいえ | P4 | あとで |

外部から送られた`priority`値は採用せず、緊急度と重要度から必ず再計算する。

### 7.4 日付関数を実装する

`src/lib/date/tokyo.ts`へ次の関数を用意する。

- 日本時間の今日を`YYYY-MM-DD`で返す。
- 期限切れか判定する。
- 本日期限か判定する。
- 今日以前か判定する。
- 月曜日から日曜日までの今週か判定する。
- 期限超過日数を返す。

テストでは実行端末のタイムゾーンに依存しない固定時刻を渡す。UTCの日付へ単純変換すると日本時間の深夜付近で日付がずれるため、境界ケースを必ず含める。

### 7.5 並べ替えと集計を実装する

### 7.6 入力スキーマを実装する

## 8. フェーズ5：Google Sheets Repository

### 8.1 APIクライアントを作る

`src/lib/sheets/client.ts`に`import "server-only"`を追加し、サービスアカウントのメールアドレスと秘密鍵からGoogle Sheets API v4クライアントを作る。

使用するスコープは原則として次だけに絞る。

```text
https://www.googleapis.com/auth/spreadsheets
```

JWT署名処理を独自実装せず、`googleapis`の認証クライアントを使用する。

### 8.2 行変換を実装する

`src/lib/sheets/mapper.ts`でA〜L列とTask型を相互変換する。

- ヘッダー行をデータとして扱わない。
- 空行は無視する。
- booleanは`TRUE`／`FALSE`と相互変換する。
- `priority`は読み込み後にも再計算し、矛盾を検知する。
- 不正行は秘密情報やセル内容をログへ出さず、行番号と分類だけを記録する。

### 8.3 Repositoryインターフェースを定義する

画面やRoute Handlerから`googleapis`を直接呼ばない。次の責務を`src/lib/sheets/repository.ts`へ集約する。

```ts
export interface TaskRepository {
  list(options?: { includeCompleted?: boolean }): Promise<Task[]>;
  findById(id: string): Promise<Task | null>;
  create(input: CreateTaskInput): Promise<Task>;
  update(id: string, input: UpdateTaskInput): Promise<Task>;
  softDelete(id: string, version: number): Promise<void>;
}
```

完了と復元は`update`に含めても、明示的なメソッドへ分けてもよい。ただし、Route Handler内へ行番号検索やセル更新処理を書かない。

### 8.4 一覧取得を実装する

1. `Tasks!A2:L`を1回で取得する。
2. 行をTask型へ変換する。
3. `is_deleted = TRUE`を除外する。
4. オプションに応じて完了済みを除外する。
5. 並べ替えは共通ドメイン関数を使用する。

一覧取得のたびに個別行APIを繰り返さない。

### 8.5 新規追加を実装する

1. `crypto.randomUUID()`でIDを作る。
2. 優先度を再計算する。
3. `status = todo`、`is_deleted = FALSE`、`version = 1`とする。
4. `created_at`と`updated_at`へ現在時刻をISO 8601で記録する。
5. `spreadsheets.values.append`でA〜L列を1回で追加する。
6. 作成したTaskを返す。

### 8.6 更新・完了・復元・削除を実装する

1. 一覧取得または検索でIDに対応する行番号を特定する。
2. リクエストの`version`とシート上の`version`を比較する。
3. 不一致なら書き込まず`409 Conflict`相当のドメインエラーを返す。
4. 更新値、`updated_at`、`version + 1`を同じ更新リクエストへまとめる。
5. 完了時は`status = done`と`completed_at`を設定する。
6. 復元時は`status = todo`とし、`completed_at`を空にする。
7. 削除時は物理行削除を行わず、`is_deleted = TRUE`とする。

Google SheetsはトランザクションDBではない。更新直前の厳密なロックは保証できないため、個人利用を前提とした楽観的競合検知として扱う。

### 8.7 エラーを分類する

Repositoryの外へGoogle APIの生エラーを出さず、次へ変換する。

| 分類 | APIでの扱い |
|---|---|
| 認証・共有設定不備 | 502 |
| 対象タスクなし | 404 |
| バージョン競合 | 409 |
| Google API使用量超過 | 429 |
| 一時的なGoogle API障害 | 502 |
| シート構造不正 | 500または運用エラー |

読み取りの一時障害には上限付きの指数バックオフを利用できる。新規追加や更新を無条件に自動再試行すると重複する可能性があるため、更新系は自動再試行しない。

### 8.8 DEVシートで接続テストする

開発用シートにだけテストタスクを追加し、一覧取得、編集、完了、復元、論理削除を確認する。テスト後、`is_deleted = TRUE`になった行を履歴として残してもよい。

## 9. フェーズ6：パスフレーズ認証とセッション

### 9.1 パスフレーズ検証を実装する

`src/lib/auth/password.ts`に次を実装する。

- 環境変数のソルト付きハッシュを解析する。
- 入力パスフレーズを同じ条件で`scrypt`へ通す。
- `timingSafeEqual`で比較する。
- 失敗理由を外部へ区別して返さない。
- 認証失敗時に短い固定遅延を加える。

### 9.2 セッションを実装する

`src/lib/auth/session.ts`に`jose`を使用した署名・検証処理を実装する。

セッション内容:

- 発行日時
- 有効期限
- トークン種別

氏名、メールアドレス、タスク情報は含めない。

Cookie設定:

```text
Name: task_session
HttpOnly: true
Secure: Productionではtrue
SameSite: Lax
Path: /
Max-Age: 90日
```

Next.js 16の`cookies()`は非同期APIとして`await cookies()`で扱う。

### 9.3 認証Route Handlerを作る

| メソッド | パス | 処理 |
|---|---|---|
| POST | `/api/auth/login` | パスフレーズ検証、Cookie発行 |
| POST | `/api/auth/logout` | Cookie削除 |

ログインAPIは成功時`204`または`200`、失敗時`401`を返す。応答本文にハッシュ、セッション値、内部エラーを含めない。

## 10. フェーズ7：タスクAPI

### 10.1 Route Handlersを作る

```text
src/app/api/
  auth/
    login/route.ts
    logout/route.ts
  tasks/
    route.ts
    [id]/
      route.ts
```

### 10.2 エンドポイントを実装する

| メソッド | パス | 処理 |
|---|---|---|
| GET | `/api/tasks` | タスク一覧取得 |
| POST | `/api/tasks` | タスク追加 |
| GET | `/api/tasks/:id` | 1件取得 |
| PATCH | `/api/tasks/:id` | 編集、完了、復元 |
| DELETE | `/api/tasks/:id` | 論理削除 |

### 10.3 共通処理順

各Route Handlerは次の順で処理する。

1. requestIdを生成する。
2. セッションを検証する。
3. 更新系ではリクエスト元を検証する。
4. JSONをZodで検証する。
5. Repositoryを呼び出す。
6. ドメインエラーをHTTPステータスへ変換する。
7. 秘密情報を除いた結果を返す。

### 10.4 レスポンス形式を統一する

成功:

```json
{
  "data": {},
  "requestId": "..."
}
```

失敗:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください"
  },
  "requestId": "..."
}
```

HTTPステータス:

| ステータス | 用途 |
|---:|---|
| 200 | 取得・更新成功 |
| 201 | 新規作成成功 |
| 204 | ログアウト・削除成功 |
| 400 | 入力不正 |
| 401 | 未認証 |
| 404 | 対象なし |
| 409 | `version`競合 |
| 429 | 使用量超過 |
| 500 | アプリ設定・内部処理エラー |
| 502 | Google Sheets API障害 |

タスクデータを含む応答には`Cache-Control: no-store`を設定する。

- [ ] 404、409、429、502
- [ ] 想定外のプロパティ拒否
- [ ] 応答とログへ秘密情報が含まれない

4. 原因となったコミットを修正し、Previewからやり直す。

コードを切り戻してもGoogle Sheets上のデータ変更は自動で戻らない。データ破損がある場合は別途バックアップから復旧する。

### 16.3 データの復旧

1. 現在のPRODシートを複製し、調査用として保持する。
2. 直近の正常なバックアップを開く。
3. A〜L列の構造を確認する。
4. 影響行だけを復旧するか、必要に応じてシート全体を差し替える。
5. `GOOGLE_SHEET_ID`を変更した場合はVercelを再デプロイする。
6. 追加、一覧、更新が正常か確認する。

### 16.4 セッションを全失効する

第三者利用の疑い、端末紛失、Cookie漏えいの疑いがある場合:

1. VercelのProduction `SESSION_SECRET`を新しいランダム値へ変更する。
2. Productionを再デプロイする。
3. 既存Cookieで保護画面へ入れないことを確認する。
4. 新しいパスフレーズでログインする。

必要に応じて`APP_PASSPHRASE_HASH`も更新する。

### 16.5 Google鍵を交換する

秘密鍵漏えいの疑いがある場合:

1. Google Cloudで新しいサービスアカウント鍵を作成する。
2. Vercelとローカルの`GOOGLE_PRIVATE_KEY`を更新する。
3. Previewで接続確認する。
4. Productionを再デプロイし、接続確認する。
5. 古い鍵をGoogle Cloudで無効化・削除する。
6. Git履歴や共有先に鍵が残っていないか確認する。

### 16.6 トラブルシューティング

| 症状 | 主な確認点 | 対応 |
|---|---|---|
| 401が続く | Cookie属性、署名鍵、有効期限 | `SESSION_SECRET`とCookie設定を確認 |
| Sheetsが403 | API有効化、共有先メール | サービスアカウントへ編集共有 |
| 秘密鍵エラー | 改行、開始・終了行 | `\\n`復元とVercel登録値を確認 |
| 429 | API呼び出し回数 | 常時取得を止め、読み取りをまとめる |
| 409 | `version`不一致 | 最新データを再取得して再編集 |
| 502 | Google APIまたは認証 | VercelログのrequestIdと分類コードを確認 |
| 日付が1日ずれる | UTC変換、端末依存 | Asia/Tokyoの共通関数を使用 |
| Previewが本番を書換 | 環境変数の対象環境 | Previewの`GOOGLE_SHEET_ID`をDEVへ戻す |
| シート読込に失敗 | 列順、タブ名、ヘッダー | `Tasks`とA〜L列を正しい構造へ戻す |

## 17. 最終Definition of Done

### 17.1 機能

- [ ] パスフレーズでログインし、90日間セッションを維持できる。
- [ ] 期日必須でタスクを追加、編集、完了、復元、削除できる。
- [ ] ダッシュボード、TODO ALL、今日まで、マトリクスが動作する。
- [ ] 優先度が緊急度と重要度から自動計算される。
- [ ] Google Sheetsへすべての変更が反映される。

### 17.2 品質

- [ ] TypeScript strictで型エラーがない。
- [ ] Lint、単体、結合、E2E、本番ビルドが成功する。
- [ ] PCとスマートフォンで操作できる。
- [ ] キーボード操作とドラッグ代替操作がある。
- [ ] エラー時に未保存であることと次の操作が分かる。

### 17.3 セキュリティ・運用

- [ ] 未認証で4画面とタスクAPIへアクセスできない。
- [ ] 秘密情報がブラウザ、Git、ログにない。
- [ ] PreviewとProductionのスプレッドシートが分離されている。
- [ ] 本番スプレッドシートが一般公開されていない。
- [ ] バックアップ、セッション失効、鍵交換、切り戻し手順を実施できる。
