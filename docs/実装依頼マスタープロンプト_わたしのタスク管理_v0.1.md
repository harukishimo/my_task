## 使い方

### 4. 完成させるプロダクト

利用者1名の個人用タスク管理アプリです。主要画面は次の4画面です。

1. ダッシュボード
2. TODO ALL
3. 今日まで
4. 優先度マトリクス

認証画面は主要4画面に含めません。公開URLからの第三者アクセスを防ぐため、ユーザー名なしの1パスフレーズ認証を実装します。

必須仕様は次のとおりです。

- タスク名、期日、緊急度、重要度を登録・編集できる
- 期日は必須で、Asia/Tokyo基準の時刻なし日付として扱う
- 緊急度と重要度からP1〜P4を必ず自動算出する
- 未完了タスクの一覧、完了、復元、論理削除ができる
- 「今日まで」には、削除されていない未完了タスクのうち`due_date <= 今日`を表示する
- 優先度マトリクスは4象限を表示し、PCではドラッグ＆ドロップ、スマートフォンでは同等の代替操作を提供する
- ダッシュボードに期限切れ、本日期限、今週期限、P1の件数と優先タスクを表示する
- 操作成功、通信中、空状態、エラー、競合を利用者が理解できる形で表示する
- PCとスマートフォンの両方で主要導線を利用できる

### 6. セキュリティとデータ境界

- ブラウザからGoogle Sheets APIを直接呼ばない
- Google認証情報、Sheet ID、パスフレーズ、セッション秘密鍵をClient Componentへ渡さない
- 秘密情報はコード、Git、テスト結果、ログ、スクリーンショットへ出さない
- `.env.local`や実値入りファイルを作成・コミットしない
- 必要な環境変数は値なしの`.env.example`と検証スキーマへ定義する
- 非公開Google Sheetsをサービスアカウントで操作する
- Preview/DEV用とProduction用のシートを分離する
- パスフレーズはソルト付きハッシュで検証し、平文を保存しない
- セッションは署名済み、90日、有効な`HttpOnly`、`Secure`、`SameSite=Lax` Cookieとする
- 主要4画面と全タスクAPIをサーバー側でも保護する
- 更新系Route Handlerで不正なクロスサイト送信を拒否する
- 個人タスクを共有キャッシュへ保存せず、APIは原則`no-store`とする
- 更新時は`version`による楽観的競合検知を行い、不一致は`409 Conflict`とする
- 削除は物理削除ではなく`is_deleted`による論理削除とする
- サーバーログへタスク本文、Cookie、秘密情報を出さない

### 7. Google Sheetsの正規スキーマ

シート名は`Tasks`とし、1行目をヘッダーとして扱ってください。

| 列 | キー | 形式 |
|---:|---|---|
| A | `id` | UUID |
| B | `title` | 1〜200文字 |
| C | `due_date` | `YYYY-MM-DD` |
| D | `is_urgent` | `TRUE/FALSE` |
| E | `is_important` | `TRUE/FALSE` |
| F | `priority` | `P1/P2/P3/P4` |
| G | `status` | `todo/done` |
| H | `completed_at` | ISO 8601または空 |
| I | `is_deleted` | `TRUE/FALSE` |
| J | `created_at` | ISO 8601 |
| K | `updated_at` | ISO 8601 |
| L | `version` | 正の整数 |

`priority`は入力値を信用せず、`is_urgent`と`is_important`からサーバーで再計算してください。不正行や空行が全体を壊さない変換層を作ってください。

### 9. 自律作業のルール

- 調査、実装、ローカルテスト、文書更新は自律的に進める
- 安全な仮定で進められる軽微な事項は判断理由を記録して進める
- 長時間作業では、現在のフェーズ、完了内容、次の作業を短く定期報告する
- 変更範囲を狭く保ち、1つの原因に対して必要以上の再設計をしない
- 同じAIが実装とレビューを担当する場合、レビュー工程では新しい文脈で差分とテスト結果を再確認する
- 各フェーズの終了時に、AIエージェント一覧の引き継ぎ形式で記録する
- 公式資料と実際のコマンド結果を優先し、未確認事項を「問題なし」と扱わない

### 10. 禁止事項

- Productionデプロイ
- Vercel、Google Cloud、Google Sheets、GitHubの本番状態変更
- 実在する秘密情報を所有者へ要求すること
- Gitへの秘密情報追加
- 許可のない`git commit`、`git push`、Pull Request作成
- 無関係なファイルや所有者の変更の破棄
- `git reset --hard`等の破壊的操作
- 要件を満たさない暫定実装を「完成」と報告すること
- テスト未実行または失敗状態で「デプロイ可能」と報告すること
- CriticalまたはHighのOpen所見がある状態で「デプロイ可能」と報告すること

### 11. 所有者へ確認して停止する条件

次の場合だけ、状況、選択肢、推奨案、影響を具体的に示して所有者へ判断を戻してください。

- 要件の正本同士に、実装結果を大きく変える矛盾がある
- データ消失につながる移行または破壊的操作が必要
- Productionや外部アカウントの変更が必要
- 課金、公開範囲、セキュリティ受容など所有者にしか決められない
- 同じ阻害要因を安全な代替手段で解消できず、コード上の作業が残っていない

Google認証情報、Sheet ID、Vercel Project IDがないことだけを理由に、初期段階で停止しないでください。外部接続以外の実装、モックテスト、文書化を先に完了してください。

### 12. 「デプロイするだけ」の完了条件

次をすべて満たした場合だけ、実装完了と判定してください。

- 要件定義書の受け入れ条件を満たす
- 主要4画面と認証画面が完成している
- Google Sheets Repositoryが実装され、モック結合テストが成功している
- 実資格情報が提供済みなら、DEVシート接続テストも成功している
- Lint、型チェック、単体、結合、UI、E2E、Productionビルドがすべて成功している
- PCとスマートフォンの主要導線が成功している
- CriticalとHighのOpenセキュリティ所見がない
- `.env.example`に必要なキーが過不足なく記載されている
- VercelとGoogle Sheetsの所有者向け設定手順が完成している
- バックアップ、スモークテスト、切り戻し手順が完成している
- 秘密情報がコード、Git差分、ログ、ブラウザ成果物へ含まれていない
- 残作業が所有者による秘密情報登録、外部サービス設定、Preview確認、Productionデプロイ、最終承認だけである

実資格情報がないために実接続を検証できなかった場合は、「コード完成、外部接続検証待ち」と正確に報告し、「完全なデプロイ準備完了」とは表現しないでください。

### 13. 最終報告形式

作業終了時は次の順で報告してください。

1. 結論
2. 実装した機能
3. 主な変更ファイル
4. 実行したコマンドと結果
5. Product、Architecture、Quality、Security、Release各Gateの判定
6. Red、Blue、Purpleの結果
7. 残余リスク
8. 所有者だけが行う残作業
9. デプロイ手順の参照先

所有者の残作業は次の形式で一覧化してください。

| 状態 | 作業 | 理由 | 手順書 |
|---|---|---|---|
| Owner action | 例: Vercelへ秘密情報を登録 | AIへ実値を渡さないため | 対応文書へのパス |

最後に「Productionデプロイは未実行」であることを明記してください。

ここまで理解したら、最初に参照文書と現状コードを調査し、短いフェーズ計画を提示してから、そのまま実装を開始してください。
